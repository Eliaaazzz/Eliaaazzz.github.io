A local Flink cluster for Beam Python, start to streaming

DirectRunner is a simulator: it ignores resume delays, fakes the clock, and forgives sins a real runner won't. The day your streaming pipeline matters, you want a real engine on your laptop. This is my complete local-Flink setup for Apache Beam Python — the exact commands, a live streaming job, the web UI to prove it, and every gotcha I hit so you don't have to. Why a real runner, locally

Everything in my unbounded sources and Watch posts — watermarks, checkpoints, defer_remainder — only means something on a runner that takes time seriously. The local FnApiRunner does not: it ignores SDF resume delays (idle sources busy-loop), and its notion of "streaming" is a polite fiction. Flink is the easiest real streaming engine to run on one machine, and it's the same engine Beam's own ValidatesRunner CI uses — when I validated my GSoC work, this exact setup ran 174 tests / 0 failures.

What you need: Java 11+, Python 3.9–3.12 with apache-beam, and a Linux-ish environment — macOS or Linux natively; on Windows, use WSL2 and do everything inside it (the gotcha list explains why that isn't optional).

Step 1 — get Flink running (two commands)

shell (WSL2 / Linux / macOS)
# 1. Download + unpack Flink (1.20.x is what current Beam targets)
curl -LO https://archive.apache.org/dist/flink/flink-1.20.1/flink-1.20.1-bin-scala_2.12.tgz
tar xzf flink-1.20.1-bin-scala_2.12.tgz

# 2. Start the standalone cluster: one JobManager + one TaskManager
./flink-1.20.1/bin/start-cluster.sh

# Sanity check — the REST API answers on :8081
curl -s http://localhost:8081/overview

That last command should return JSON like {"taskmanagers":1,"slots-total":4,…,"flink-version":"1.20.1"}, and http://localhost:8081 now serves the Flink Web UI (WSL2 forwards localhost to Windows automatically):

Out of the box you get 4 task slots (conf/config.yaml → taskmanager.numberOfTaskSlots) — plenty for local work. Stop everything later with bin/stop-cluster.sh.

Step 2 — a genuinely streaming pipeline

A tick every second, counted in 10-second event-time windows, forever. Small enough to read in one breath, streaming enough to exercise watermarks and checkpoints:

blog_stream_demo.py
import logging

import apache_beam as beam
from apache_beam.options.pipeline_options import PipelineOptions
from apache_beam.transforms.periodicsequence import PeriodicImpulse
from apache_beam.transforms.window import FixedWindows

_LOGGER = logging.getLogger("blog_stream_demo")


def log_count(kv):
  window_key, n = kv
  _LOGGER.warning("window closed: %s ticks=%d", window_key, n)
  return kv


def run():
  options = PipelineOptions([
      "--runner=FlinkRunner",
      "--flink_master=localhost:8081",
      "--flink_version=1.20",
      "--environment_type=LOOPBACK",
      "--streaming",
      "--job_name=ticks-every-second",
      "--parallelism=1",
  ])
  # Ask Flink to checkpoint every 10s so the Checkpoints tab has a story.
  # (If your SDK version rejects a --checkpointing_interval flag, this
  # options escape hatch always works.)
  options._all_options["checkpointing_interval"] = 10000

  with beam.Pipeline(options=options) as p:
    _ = (
        p
        | "TickEverySecond" >> PeriodicImpulse(fire_interval=1.0)
        | "Window10s" >> beam.WindowInto(FixedWindows(10))
        | "One" >> beam.Map(lambda _: ("ticks", 1))
        | "CountPerWindow" >> beam.CombinePerKey(sum)
        | "Log" >> beam.Map(log_count))


if __name__ == "__main__":
  logging.basicConfig(level=logging.INFO)
  run()

Two options carry all the weight:

  • --flink_master=localhost:8081 — submit to the real cluster. (Omit it and Beam spins up a throwaway mini-cluster instead: convenient, but then there's no UI to look at.)
  • --environment_type=LOOPBACK — the worker harness runs inside your Python process, so no Docker images, instant logs in your terminal, and your local files are just there. Perfect for development; for production you'd let workers run in containers instead.

Step 3 — submit, then watch it actually run

shell
python blog_stream_demo.py
# first run: Beam downloads beam-runners-flink-1.20-job-server-*.jar
# into ~/.apache_beam/cache/jars — one-time, ~250 MB
# then: INFO ... Job state changed to RUNNING
#       WARNING blog_stream_demo window closed: ('ticks', 10) ...

The process stays in the foreground — that's correct, your terminal is a LOOPBACK worker now. Open the job in the UI and you can watch the pipeline as Flink sees it:

Worth a minute of staring: Beam's runner translation fused the five Python transforms into three Flink vertices — Source: Impulse → TickEverySecond, the windowing map, and CountPerWindow/GroupByKey → Log — connected by HASH exchanges. The "Low Watermark" column is the event-time frontier from part one of the streaming story, live on a dashboard.

Step 4 — checkpoints, for real this time

Because we set a checkpoint interval, Flink snapshots the whole pipeline every ten seconds — including the windowed sums buffered inside CombinePerKey:

That table is the difference between a simulator and a runner. Kill the TaskManager mid-run and Flink restores from the latest checkpoint — the same machinery that makes an SDF's residual durable when a source calls defer_remainder. When I soak-tested unbounded SDFs on exactly this setup, that machinery is where I found (and fixed, #39191) a state leak: every self-checkpoint registered a fresh Flink state entry and never cleaned it up, which OOMed long-running streams.

The gotcha list

Everything here cost me an evening once. Windows-specific ones first:

  • Run the client inside WSL2, not native Windows. On native Windows, the auto-started job server trips over drive-letter paths (the colon in C:\… reads as a separator), and the gradle/tox harness around Beam's own test suites hardcodes POSIX sh. Everything in this post — Python included — runs inside WSL2.
  • Keep the session that started Flink alive. Daemons launched from a WSL shell can die with it (SIGHUP) — if :8081 mysteriously refuses connections a minute later, that's what happened. Start the cluster from a shell you keep open, or wrap it in setsid/tmux.
  • Let java.exe through the firewall the first time Windows asks, or the job submission waits until it times out.
  • Don't mix Docker Desktop with LOOPBACK. With environment_type=DOCKER the worker container's localhost is not your machine, and the artifact channel breaks in confusing ways. LOOPBACK sidesteps all of it locally.
  • Long soaks with PeriodicImpulse: on SDKs before the #39191 fix, self-checkpointing SDFs leak runner state on Flink — fine for demos, visible after hours. Upgrade, or keep soaks short.
  • --flink_version must match the cluster (here 1.20), because it selects which job-server jar Beam downloads.
