Teaching Python pipelines to never stop

For a decade, Apache Beam's Python SDK had no way to read a custom real-time stream — that was a Java-only superpower. This is the full story, written so you can follow it with zero streaming background: what streaming actually is, how Splittable DoFns work, how to build your own source, and how it held up across four runners.

The decade-old gap

Here is a sentence that surprised me when I first read it: until June 2026, if you wanted an Apache Beam pipeline written in Python to read from your own real-time system — an internal message queue, a change-data-capture feed, a socket of sensor readings — there was no supported way to do it.

Java users have had one since Beam's beginning: a class called UnboundedSource, the thing under the hood of connectors like KafkaIO. Python users had BoundedSource for finite data and… that was it. Issue #19137 — "Add UnboundedSource interface and SDF wrapper for Python SDK" — sat open for years. The official docs for writing Python connectors described bounded reads only.

For Google Summer of Code 2026, working with my mentor Yi Hu at Google, I closed that gap: PR #38724 added the Python SDK's first public UnboundedSource API — an UnboundedSource / UnboundedReader / CheckpointMark trio with Java-aligned semantics, executed by a single Splittable DoFn wrapper — and it merged after review by the Beam PMC Chair. It runs, verified, on DirectRunner, Prism, Flink, and Google Cloud Dataflow.

This post is the tutorial I wish had existed when I started. It assumes nothing: not Beam, not streaming, not distributed systems. If you already know Beam, jump to Splittable DoFn or straight to the tutorial.

Beam, in five minutes

Apache Beam is a way to describe a data processing job once and run it on many different engines. You write a pipeline — a graph of processing steps — in Python (or Java, or Go), and hand it to a runner: your laptop (DirectRunner), an Apache Flink or Spark cluster, or Google Cloud Dataflow. Same code, different engine.

Three words carry most of the model:

  • A PCollection is a dataset flowing through the pipeline — lines of a file, events from a queue.
  • A PTransform is a step that turns one PCollection into another — parse, filter, count.
  • A runner executes the graph, splitting work across many machines.

A complete pipeline, so you've seen one:

wordcount.py
import apache_beam as beam

with beam.Pipeline() as p:
  (p
   | beam.io.ReadFromText('shakespeare.txt')      # PCollection of lines
   | beam.FlatMap(lambda line: line.split())      # PCollection of words
   | beam.combiners.Count.PerElement()            # PCollection of (word, n)
   | beam.Map(print))

Read it top to bottom: read a file, split into words, count each word, print. The | is just Beam's way of chaining steps. Run it and the process finishes when the file is exhausted — because a file can be exhausted. Hold that thought.

What makes streaming hard

Data comes in two shapes. A bounded dataset is finite — yesterday's logs, a database snapshot. You can read it, reach the end, and declare victory. An unbounded dataset has no end — the clicks are still happening, the sensors are still measuring. A pipeline reading it should, in principle, run forever.

Running forever sounds simple — just loop, right? — until you ask the operational questions. Any real answer to "read a stream inside a distributed engine" has to solve four problems at once:

  • Parallelism. One Python process can't drink a firehose. The read must split into independent pieces (think: one per Kafka partition) that different workers own.
  • Checkpointing. Workers crash. Machines get preempted. After a restart, the read must resume exactly where it left off — no lost records, no duplicates.
  • Watermarks. If you're counting events "per minute", when is the 14:03 minute complete? A watermark is the source's running promise: "you will not see records with event times earlier than T from me again." It's what lets time-based windows ever fire.
  • Yielding. When the stream is quiet, the reader must give the worker back — and be resumed later — instead of hogging a thread in a spin loop.

Java's UnboundedSource API is a checklist of exactly these concerns. The Python SDK never got that class — and by the time anyone might have ported it, Beam had moved to a newer, more general engine for all sources. To understand what I actually built, you need to meet that engine.

Splittable DoFn, gently

A regular DoFn (the function inside a ParDo step) is atomic: it takes an element, does its work, returns. The runner's only knobs are "run it" and "run it again". That's fine when each element means a millisecond of work. It's terrible when one element means "read this entire 2 TB file" — or worse, "read this topic forever".

A Splittable DoFn (SDF) fixes this by making the work itself a first-class, divisible object called a restriction. For a file, the restriction is a byte range [0, 2TB). For our stream it will be "the source, from this checkpoint onward". Alongside the element, the DoFn receives a restriction tracker holding that restriction, and processing becomes a polite negotiation:

  1. Before producing each piece of output, the DoFn asks tracker.try_claim(position) — "may I process up to here?"
  2. If it returns True, do the work and emit.
  3. If it returns False, the runner has decided to take the rest of the work back. Stop immediately and return.

Why would the runner say no? Because at any moment it may split the restriction into a primary (what you've claimed so far) and a residual (everything after). The residual is durably saved and scheduled to run later — possibly on a different machine. That one mechanism is load balancing and checkpointing and crash recovery, unified:

Three more SDF pieces complete the kit:

  • defer_remainder(delay) — the DoFn can split itself: "checkpoint me here, wake me up in five seconds." This is how an unbounded read politely yields when there's no data.
  • Watermark estimators — a small object through which the DoFn reports event-time progress to the runner (watermark_estimator.set_watermark(t)).
  • @beam.DoFn.unbounded_per_element() — a decorator that tells the runner "this DoFn may do infinite work per element," which is what makes the output PCollection officially unbounded and the pipeline a streaming one.

SDF is the machinery Beam recommends for every new connector. It's powerful — and, used raw, it's a lot: restrictions, trackers, providers, estimators, coders for all of the above. That tension is exactly where this project lives.

The design: a familiar API on a modern engine

If SDF can already express unbounded reads, why build an UnboundedSource API at all? Three reasons convinced us:

  • The mental model matches real systems. "A reader with a resumable position that periodically snapshots a checkpoint and later acks it" is how a Kafka consumer, a Pub/Sub subscription, or a CDC log client actually behaves. People maintaining such systems shouldn't have to re-derive restriction-tracker theory to connect one.
  • A decade of Java connectors becomes portable. With matching class shapes — split, create_reader, checkpoint coders, watermarks — porting a Java connector to Python is mechanical rather than a redesign.
  • The hard SDF parts get solved once, centrally. Bundle time caps, reader reuse, watermark plumbing, checkpoint finalization: every connector needs them, and nobody should hand-roll them per connector.

So the shape of #38724 is: a public API of three small classes, and one internal Splittable DoFn that knows how to run any of them.

Tutorial: build a source from scratch

Let's build a complete, honest unbounded source: a rate-limited counter. It emits the integers 0, 1, 2, … at a fixed rate — say five per second — each stamped with an event time. It's the "hello world" of streaming, and it exercises every part of the API: pacing (sometimes there's no data yet), checkpointing (resume mid-count), watermarks (windows can fire), and even a finite end, so you can watch a streaming pipeline terminate gracefully.

Everything below targets Beam ≥ 2.68 with the merged API (apache_beam.io.unbounded_source). One caveat before you type: put the source in its own module (here ticker.py), not in your main script — the pitfalls section explains why.

Step 1 — the checkpoint mark: "where was I?"

A CheckpointMark is the little token of state that makes resumption possible. Ours only needs one number: the last index we handed to the pipeline.

ticker.py — part 1
import time

import apache_beam as beam
from apache_beam import coders
from apache_beam.io.unbounded_source import (
    CheckpointMark, UnboundedReader, UnboundedSource)
from apache_beam.utils.timestamp import (
    MAX_TIMESTAMP, MIN_TIMESTAMP, Timestamp)

# A fixed event-time origin for our ticks (2025-01-01T00:00:00Z).
EVENT_BASE = Timestamp(1735689600)


class TickCheckpoint(CheckpointMark):
  """Remembers the last tick index already handed to the pipeline."""
  def __init__(self, last_index):
    self.last_index = last_index

  def finalize_checkpoint(self):
    # Called only AFTER the runner has durably committed the bundle
    # containing these ticks. In a real connector this is where you
    # acknowledge messages upstream (e.g. ack a queue, commit offsets).
    # Our counter has nothing to ack, so we just note it happened.
    print(f'[finalize] committed through tick {self.last_index}')

That finalize_checkpoint hook deserves a pause, because its timing is the entire point. It does not run when the checkpoint is created — it runs after the runner has made the outputs durable. If the worker dies in between, finalize never fires, the checkpoint is restored, and the records are re-read. That ordering is what makes "ack the message queue" safe: you never acknowledge data the pipeline could still lose.

Step 2 — the reader: a cursor with manners

An UnboundedReader is a stateful cursor over the stream. The contract is small but strict, and two return values mean very different things:

  • start() / advance() return True — "I've moved to a new record; ask me for it."
  • They return False — "no data right now." Not the end of the world, not the end of the stream. The wrapper will checkpoint and try again later.
ticker.py — part 2
class TickReader(UnboundedReader):
  """Emits tick i no earlier than (start of run) + i / rate seconds."""
  def __init__(self, count, rate, start_index):
    self._count = count            # how many ticks exist in total
    self._rate = rate              # ticks per second
    self._next = start_index       # next index to emit
    self._current = None           # index most recently emitted
    self._exhausted = False
    # Pace as if tick 0 happened when the run began; resuming from a
    # checkpoint keeps the same cadence without replaying old waits.
    self._t0 = time.time() - start_index / rate

  def start(self):
    return self.advance()

  def advance(self):
    if self._next >= self._count:
      self._exhausted = True       # a real stream would never do this
      return False
    if time.time() < self._t0 + self._next / self._rate:
      return False                 # next tick isn't due yet: "no data NOW"
    self._current = self._next
    self._next += 1
    return True

  def get_current(self):
    return self._current

  def get_current_timestamp(self):
    # Event time of the current record.
    return EVENT_BASE + self._current / self._rate

  def get_watermark(self):
    # Our promise: "no future record will be older than this."
    if self._exhausted:
      return MAX_TIMESTAMP         # the stream is truly over
    if self._current is None:
      return MIN_TIMESTAMP         # haven't read anything yet
    return EVENT_BASE + self._current / self._rate

  def get_checkpoint_mark(self):
    last = self._current if self._current is not None else self._next - 1
    return TickCheckpoint(last)

  def close(self):
    pass                           # a real reader closes its connection

Look at get_watermark for a moment. For our counter the watermark simply tracks the last emitted event time — ticks arrive in order, so nothing older can appear. Returning MAX_TIMESTAMP is the special move: it tells the runner this reader is permanently done. Every event-time window downstream can now close, fire, and let the pipeline finish. A Kafka-style connector would just never return it.

Step 3 — the source: the factory and the splitter

ticker.py — part 3
class TickSource(UnboundedSource):
  """A rate-limited counting stream: 0..count-1 at `rate` per second."""
  def __init__(self, count=60, rate=5.0):
    self._count = count
    self._rate = rate

  def split(self, desired_num_splits, options=None):
    # Our ticks come from one logical stream, so keep one split.
    # A Kafka-style source would return one sub-source per partition.
    return [self]

  def create_reader(self, options, checkpoint_mark):
    start = 0 if checkpoint_mark is None else checkpoint_mark.last_index + 1
    return TickReader(self._count, self._rate, start)

  def get_checkpoint_mark_coder(self):
    # How the runner serializes our checkpoint for durable storage.
    # PickleCoder is fine to start; real connectors write a compact one.
    return coders.PickleCoder()

  def default_output_coder(self):
    return coders.VarIntCoder()

create_reader is where recovery becomes visible: the runner hands you back the last durable TickCheckpoint, and you position the new reader at last_index + 1. Crash at tick 41, resume at tick 42 — no gaps, no repeats.

Step 4 — the payoff: a streaming pipeline in one line

All of that plugs into a pipeline through the ordinary beam.io.Read:

run_ticker.py
import apache_beam as beam
from apache_beam.options.pipeline_options import PipelineOptions
from apache_beam.transforms import window

from ticker import TickSource

opts = PipelineOptions(streaming=True)

with beam.Pipeline(options=opts) as p:
  (p
   | 'Ticks'  >> beam.io.Read(TickSource(count=60, rate=5.0))
   | 'Window' >> beam.WindowInto(window.FixedWindows(2))   # 2s event-time windows
   | 'One'    >> beam.Map(lambda i: ('ticks', 1))
   | 'Count'  >> beam.CombinePerKey(sum)
   | 'Show'   >> beam.Map(print))

Sixty ticks at five per second is twelve seconds of stream; two-second windows should each hold ten ticks. Run it (python run_ticker.py) and watch:

output
('ticks', 10)
('ticks', 10)
('ticks', 10)
('ticks', 10)
('ticks', 10)
('ticks', 10)
[finalize] committed through tick 59

Every one of those lines is a small miracle of coordination. A window like [00:00:02, 00:00:04) fired only because your reader's watermark crossed 00:00:04 — the runner asked your source "will there be more data before this moment?", your watermark said no, and the window sealed itself. When the counter ran out and the watermark jumped to MAX_TIMESTAMP, the final window fired and the "infinite" pipeline shut down cleanly. You've just watched event time, checkpointing, and termination cooperate.

Going parallel

To spread a source across workers, return several independent sub-sources from split. The SDK's own test source splits the counter into even/odd sub-streams: two sources with modulus=2 and residue=0,1, each a complete non-splittable source of its own. Beam then runs one reader per split, each with its own checkpoint. Kafka's version of this sentence is "one split per partition."

Run it: same file, three engines

The point of Beam is that run_ticker.py doesn't change as the engine does.

DirectRunner (above) is what you get by default — perfect for development. Two honest caveats from testing the wrapper there: the local runner ignores resume delays, so an idle source busy-loops instead of napping between polls, and it processes windows a touch eagerly. Fine for tests; not a performance preview.

Flink, the workhorse open-source streamer. With a local Flink cluster running, the same file needs only options:

shell
python run_ticker.py \
  --runner=FlinkRunner \
  --flink_master=localhost:8081 \
  --environment_type=LOOPBACK \
  --streaming

Here defer_remainder is honored for real: an idle tick source checkpoints, sleeps its poll interval, and resumes — you can watch bundles and checkpoints line up with the data gaps in the Flink UI.

Google Cloud Dataflow, the managed option, where the SDF machinery runs on Runner v2:

shell
python run_ticker.py \
  --runner=DataflowRunner \
  --project=$PROJECT --region=us-east1 \
  --temp_location=gs://$BUCKET/tmp \
  --streaming --experiments=use_runner_v2 \
  --extra_package=./dist/ticker-0.1.tar.gz   # ship ticker.py to workers!

That last flag matters — workers are fresh machines that have never heard of ticker.py. Package your source (or install it on the workers); more in pitfalls.

What the wrapper does for you

Between your tidy three classes and the runner sits the piece I spent most of the summer on: ReadFromUnboundedSource, the internal SDF that executes any UnboundedSource. What it handles is exactly the list of things you'd otherwise debug at 2 a.m.:

  • The claim loop. Each bundle, the wrapper drives your reader — start/advance, try_claim against the tracker, emit with the record's event time, update the watermark — until the runner splits, the stream goes quiet, or a cap is hit.
  • Bundle caps: 10,000 records or 10 seconds. A firehose source would otherwise keep one bundle alive forever — blocking checkpoints, watermark advancement, and autoscaling signals. The wrapper self-checkpoints at either cap, mirroring the Java runner's OutputAndTimeBounded…Invoker semantics. (The caps are constructor-tunable.)
  • Polite idling. When advance() returns False, the wrapper checkpoints and schedules its own resumption via defer_remainder(poll_interval) — one second by default — so a quiet stream costs almost nothing on runners that honor resume delays.
  • A reader cache. Resuming a residual doesn't mean reconnecting to your upstream system from scratch: the wrapper parks live readers keyed by (source, checkpoint) and reuses them on resume, with idle eviction (60 s) and a size cap (100) as backstops. For a real connector this is the difference between "resume" and "reconnect storm."
  • Exactly-once finalization. Your finalize_checkpoint is registered as a bundle finalizer and invoked only after the runner commits the bundle — and only once, even if the same checkpoint object gets multiple chances.
  • Watermark discipline. Your get_watermark feeds a manual estimator with a monotonic guard, and MAX_TIMESTAMP cleanly ends the restriction so downstream windows can close. Drain is supported by truncating the remaining work.

None of this is visible in run_ticker.py. That's the design working.

Pitfalls I hit so you don't have to

A tutorial that skips the failure modes isn't complete. These are the walls I personally walked into while validating the wrapper on real runners.

1. Your source class must be importable on workers

My first Dataflow run died with Can't get attribute 'TickSource' on <module 'sdk_worker_main'>. Classes defined in your launch script live in __main__, and remote workers reconstruct objects by importing them — there is no __main__ to import from. Put sources in a real module and ship it (--extra_package, a pip install, or an sdist via --sdk_location). This applies to every distributed runner, not just Dataflow.

2. DirectRunner is a simulator, not a benchmark

The local FnApiRunner ignores defer_remainder's delay — an idle source resumes instantly, busy-looping through empty bundles. My trickle-feed demo cut ~176 checkpoints per second locally where Flink would cut ~1 per poll interval. Correctness testing: great. Extrapolating performance: don't.

3. Deep self-checkpoint chains can hit Python's C-recursion guard

An unbounded SDF that self-checkpoints thousands of times in one local run eventually blew up in the FnApiRunner's metrics consolidation with a RecursionError — each sub-bundle nested another lazy consolidate(chain(...)), and CPython 3.12+ caps C-level recursion regardless of sys.setrecursionlimit. Pre-existing runner behavior, easy to hit once sources can checkpoint freely; keep local soak tests modest.

4. Streaming capacity is regional weather

Two Dataflow submissions failed with ZONE_RESOURCE_POOL_EXHAUSTED before any worker started — us-central1 was simply out of the machine type that afternoon. Same job, us-east1: placed immediately. Region-hop before you debug your own code.

5. Watermarks are a promise — never take one back

The estimator refuses watermark regressions, and it's right to: downstream state is discarded the moment a window closes. Emit conservative watermarks (the oldest thing you might still deliver), advance them monotonically, and treat MAX_TIMESTAMP as a one-way door.

What landed, and what it unlocked

  • #38724 — the UnboundedSource API + SDF wrapper. Merged.
  • #38892 — a ValidatesRunner test locking the behavior in on portable runners, so every future runner change is checked against it. Merged.
  • #39529 — the missing chapter of the official Python connector guide: how unbounded reads map onto SDF. In review.
  • #39191 — found while soaking unbounded SDFs on Flink: every self-checkpoint leaked a Flink state entry, eventually OOMing long-running streams. Fixed with a stable residual-state lifecycle. Merged.
  • #39331 — the same self-checkpoint machinery for the portable Spark runner, the last big engine without it. In review.

And one more thing it unlocked: once Python could run polling loops on SDF properly, it became natural to port Beam's most elegant polling abstraction — the Watch transform. That's part two of this story.
