The portable loop, in one picture

Unlike Flink — where the Beam client talks to the cluster almost directly — the Spark runner goes through Beam's portability front door: a small Java process called the job server that accepts your pipeline as a language-neutral proto, translates it into Spark's RDD API, and submits the result as a Spark application.

The lovely consequence: your pipeline file doesn't mention Spark anywhere except the endpoint option. The uncomfortable consequence lives at the end of this post.

Step 1 — the job server

Two ways to get one, both fine:

option A — docker (easiest)
docker run --net=host apache/beam_spark3_job_server:latest \
  --spark-master-url=spark://localhost:7077
option B — the jar (what I run; no Docker in WSL2)
# build once from a Beam checkout…
./gradlew :runners:spark:3:job-server:shadowJar
# …then run it against your cluster (or local[4] for embedded Spark)
java -jar beam-runners-spark-3-job-server-*.jar \
  --job-port 8099 --artifact-port 8098 --expansion-port 8097 \
  --spark-master-url spark://localhost:7077

When it's up, port 8099 is listening and every Beam pipeline with --job_endpoint=localhost:8099 lands here. With --spark-master-url local[4] you don't even need a cluster — the job server embeds one. But we came for the real thing:

Step 2 — a real (tiny) Spark cluster

shell (WSL2 / Linux / macOS)
curl -LO https://archive.apache.org/dist/spark/spark-3.5.0/spark-3.5.0-bin-hadoop3.tgz
tar xzf spark-3.5.0-bin-hadoop3.tgz && cd spark-3.5.0-bin-hadoop3

./sbin/start-master.sh --host localhost --port 7077 --webui-port 8080
./sbin/start-worker.sh  spark://localhost:7077 --cores 2 --memory 2g

Step 3 — run a pipeline

Note what's absent below: any mention of Spark beyond the endpoint. This is the same shape of file as the Flink post's demo — that's the whole point of Beam.

blog_spark_demo.py
import logging
import time

import apache_beam as beam
from apache_beam.options.pipeline_options import PipelineOptions

WORDS = [
    "streaming", "pipelines", "should", "not", "care", "which", "engine",
    "runs", "them", "beam", "spark", "portable", "runner", "loopback",
]


def slow_pair(word):
  time.sleep(0.05)  # keep the stage on the UI long enough to look at
  return (word, len(word))


def log_pair(kv):
  logging.warning("word=%s len=%d", *kv)
  return kv


def run():
  options = PipelineOptions([
      "--runner=PortableRunner",
      "--job_endpoint=localhost:8099",
      "--environment_type=LOOPBACK",
      "--job_name=word-lengths-on-spark",
  ])
  with beam.Pipeline(options=options) as p:
    _ = (
        p
        | "Words" >> beam.Create(WORDS * 150)
        | "Pair" >> beam.Map(slow_pair)
        | "MaxLen" >> beam.CombinePerKey(max)
        | "Log" >> beam.Map(log_pair))


if __name__ == "__main__":
  logging.basicConfig(level=logging.INFO)
  run()

Step 4 — read the Spark UI like a translation

While the job runs, the driver serves the standard application UI on http://localhost:4040 — and its Stages tab is a little Rosetta stone. You wrote Create | Map | CombinePerKey; Spark is executing repartition, mapPartitionsToPair, and foreach stages generated by Beam's translators:

Those java file names in the stage descriptions are exactly where the portable Spark runner lives in the Beam codebase — the same files my current PR touches.

Where streaming stops — and why that's my problem now

Try the Flink post's PeriodicImpulse demo against this job server and you'll hit the wall that's been open since 2019 as issue #19468: the portable Spark runner cannot run unbounded Splittable DoFns. Beam's own test suite name-skips every test_sdf* case on Spark.

The missing piece is precise: when an unbounded SDF pauses itself with defer_remainder, the runner must catch the returned residual, store it durably, and re-schedule it — and honor bundle finalization on commit. Flink implements that hand-off; the portable Spark runner historically dropped it, so an unbounded source either never yields or loses its place. That's the exact machinery my streaming work depends on, so closing it became my job:

  • #39331 — SDF self-checkpointing and bundle finalization for the portable Spark runner (in review): catch the residual in-call, resume it, and fire finalization callbacks — the same contract the UnboundedSource wrapper relies on.
  • On top of it I've validated locally a cross-batch residual relay with watermark feeding — unbounded SDF output flowing across Spark micro-batches with event-time windows firing exactly. Streaming Spark for Python is a longer road, but it's walkable.

Until then, the honest guidance: Spark runner for batch Beam Python — works well, as you just saw. For streaming, use Flink or Dataflow.

Gotchas

  • Keep the client process alive. With LOOPBACK, your Python process hosts the workers' harness — Ctrl-C'ing the client kills the job's UDF execution.
  • WSL2: copy big jars onto ext4. Class-loading a ~300 MB shadow jar through the /mnt/c 9p filesystem is painfully slow; cp it to ~ first.
  • The job server is quiet by design — the shadow jar ships no logging backend, so don't wait for a "ready" banner; probe port 8099.
  • One job server, one cluster mode. Restart it to switch between local[4] and spark://… — it binds its master URL at startup.
  • 4040 only exists while a driver runs. If you want to inspect a finished job, check the master UI's Completed Applications instead.
