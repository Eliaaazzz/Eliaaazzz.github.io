blog / agent harnesses · a benchmark, not an opinion

The code came out identical. The tests didn't.

I'd just read enough about graph engineering to be enthusiastic about it, which is a dangerous state to make architecture decisions in. So I built the same backend feature twice — once through a typed-state graph, once through a feedback loop, both driving Codex on the same spec — and measured what the extra wiring actually bought. It was not what I expected, and one of the two runs I had to throw in the bin.

The question

There are two camps about how to point a coding agent at a task, and in 2026 they are both loud. One says: wire your agents into an explicit graph — typed state on the edges, deterministic routers, gates you can inspect when something goes wrong at 3am. The other says: stop building scaffolding, a good model in a tight loop with a compiler will beat your boxes and arrows, and Claude Code and Codex are the existence proof.

Both arguments are persuasive when you read them. Neither comes with numbers. The debate I read most recently cited engagement counts on X as evidence, which is a measure of something, just not of this.

So: same feature, same spec, same model, two harnesses, and a scoreboard I couldn't argue my way out of afterwards. My prior was that the graph would win. I wanted to know by how much, and on which axis.

Rules of the game

The feature is one I actually wanted in my nutrition app's backend: an adaptive TDEE estimator. Instead of assuming your maintenance calories from a textbook formula, it measures them from the energy-balance identity — over a window, what you ate minus what your body mass did. MacroFactor built a business on this. It is about 300 lines of Java, it touches no database, and it is stuffed with the kind of edge cases that separate code that works from code that looks like it works: outlier scale readings, half-logged days, duplicate entries, not enough data to say anything honest at all.

I wrote the spec first and froze it. Every formula, every threshold, every exception message pinned down — 7700 kcal per kg, a day under 500 kcal doesn't count as logged, drop weight readings more than 3 kg from the window median, clamp the answer between 1× and 2.5× BMR, round to the nearest ten. Both harnesses got that file, byte for byte.

Then, before either one ran, I wrote something neither of them would ever see: 23 acceptance tests, expected values worked out by hand from the spec. A held-out set. If you only score an agent on the tests it wrote itself, you are measuring its confidence, not its correctness.

in plain words

Think of it as an exam. I wrote the syllabus and handed it to both students. Then I wrote the exam paper and locked it in a drawer. Neither of them got to set their own questions — which is exactly what happens when you let an agent write both the code and the tests and then celebrate the green checkmark.

One more step, and it's the one people skip: I hand-wrote a reference implementation of the spec myself and ran the held-out suite against it. 23/23. If my exam paper had a typo in it, I'd rather find out before it was grading anybody.

The rest is plumbing, kept deliberately identical: two isolated git worktrees off the same commit, Codex gpt-5.5 at the same reasoning effort for both, the same Gradle harness compiling and running the tests, and both runs executed sequentially so neither was fighting the other for CPU while I timed it.

The two harnesses

I built each one to the best practices its own literature recommends, not to a straw man of it.

The graph. Every model node returns a JSON-Schema-validated object, not prose — so state moves along the edges as data. Nodes only see the slice they need. Anything with a known rule is plain code rather than a model call: the window filter, the compile gate, the test gate, the join. Routing is a guard condition I can read:

graph.mjs
// two review lenses, fanned out, joined and de-duplicated in code —
// the model never decides where control flow goes next
const [edge, math] = await Promise.all([lens('edge', ...), lens('math', ...)]);
const blocking = dedupe([...edge.findings, ...math.findings])
                   .filter(f => f.severity === 'BLOCKING');

if (blocking.length > 0) await patch(blocking);   // this edge, or no edge

The piece that turned out to matter: writing the tests is its own node, with its own context, fed by a decomposed contract rather than by the implementation. Its instructions said, in effect: you may open the main code to check a method signature, but every expected value you assert has to come from the spec — and if the implementation disagrees with the spec, your test should fail.

The loop. One agent, one long-lived session, told to write the feature and its tests. Then the cycle the reflect-refine literature actually recommends, not the naive version: the loop is driven by an external verifier — the compiler and the test run — because self-assessment without a hard signal is the well-documented way these loops fool themselves. When the build goes green, an independent critic gets a fresh read-only session and a scoring rubric. Failures become verbal lessons appended to a REFLECTIONS.md that is re-injected on every subsequent attempt, Reflexion style. Bounded at five iterations. Convergence is a threshold in my code, not a vibe in the model's head.

The run I threw away

Here is the part I'd quite like to leave out.

codex exec resume doesn't accept the -C working-directory flag that codex exec does. I found that out the sensible way, with a smoke test, and fixed it by dropping -C and setting the child process's working directory instead. Which I did — in the Gradle helper. Not in the Codex helper.

So the graph's second run executed entirely inside my main repository. It couldn't find the spec file, because the spec lived in the worktree. And instead of failing, it did the most reasonable-looking thing available to it: it invented a plausible TDEE specification from the surrounding code, implemented that, wrote tests for it, and — this is the detail that stuck with me — created a test file called SpecTdeeMdMissingTest.java to document that the spec it had been told was authoritative was nowhere to be found. Then it reported success. Every gate I'd built was green, because every gate was measuring the wrong tree.

Nothing tracked was modified, the stray files came back out cleanly, and I reran from zero. But the lesson is not "I made a typo". It's that an agent harness needs the same guard rails as the thing it's testing, and my elaborate typed-state graph had no assertion anywhere that it was standing in the right directory. The fix is four words long and now runs before every model call:

runner.mjs
if (!fs.existsSync(path.join(cwd, 'SPEC-TDEE.md')))
  throw new Error(`spec missing in ${cwd} — wrong working dir`);

Every number below comes from the clean rerun.

What came back

Read the first row again. A dead heat on the metric I'd spent the most care designing. The graph cost 2.3× the output tokens and roughly twice the wall clock to arrive at the same score.

If I'd stopped there — and I nearly did, because that's a clean, publishable, counterintuitive result — I would have written a post arguing that graph engineering is expensive ceremony. That post would have been wrong.

The tie that wouldn't break

Twenty-three hand-written tests failing to separate two implementations can mean two very different things: the implementations are genuinely equivalent, or my exam was too easy. Those deserve different conclusions, so I went and found out.

I wrote a differential harness: 20,000 seeded random requests — null dates, duplicate entries, weights of zero and negative weights, calorie values straddling the 500 boundary, windows outside the legal range, missing BMR inputs — with every result dumped to a CSV. The same file compiled into all three trees: graph, loop, and my hand-written reference. Identical seeds, identical inputs, so any behavioural difference anywhere shows up as a line in a diff.

diff
graph vs ref   0 divergences
loop  vs ref   0 divergences
graph vs loop  0 divergences

Byte for byte, 60,000 lines, three independent implementations. So it wasn't my exam being easy. On a spec this precise, the harness topology genuinely does not change what the model gets right. The loop camp is correct about that, and I'd been quietly assuming otherwise.

Mutation testing settles it

Which leaves the other half of the deliverable. Both harnesses shipped a test suite, and those suites are what will be standing between this code and the next person who edits it. One is 788 lines and one is 360. Does the difference buy anything, or is it just more typing?

The way to answer that is to break the code on purpose. I wrote eleven mutations, each a plausible misreading of the spec rather than random noise — the kind of thing a tired human or a hurried model actually does:

  • caloriesIn >= 500 becomes > 500
  • the even-count median takes the upper middle instead of the mean of the two
  • the outlier band tightens from <= 3.0 to < 3.0
  • each sufficiency threshold slips by one
  • rounding to the nearest ten becomes truncation
  • duplicate dates resolve first-wins instead of last-wins
  • the female Mifflin constant shifts from −161 to −165

Apply one, run only that worktree's own suite, record whether anything went red, restore, repeat.

There it is. Every mutation the loop's tests missed is a threshold or a boundary — the exact places where code passes a happy-path test and quietly returns the wrong number for somebody at 10 logged days instead of 11.

And a detail that made me put my coffee down: the graph's suite killed three mutants that my own held-out suite couldn't. My exam paper never places a weight reading exactly 3 kg from the median, and my one female-BMR case happens to round to the same ten-kcal bucket under both the correct constant and the broken one. The agent's tests were stricter than the tests I'd written by hand to grade it with.

The critic that saw it and shrugged

The loop's independent critic was not asleep. Its own written verdict opens by warning that a green build proves nothing here, "because the tests were written by the same agent that wrote the code, so a shared misreading of the spec passes silently." It then listed four concrete coverage gaps. Three of them are, precisely, mutations its suite went on to miss: the even-count median, the exact thresholds, the rounding and clamp boundaries.

It saw the problem, named the problem, graded every instance of it MINOR, scored edge-case coverage 8 out of 10, and approved. My convergence rule only blocked on BLOCKING findings and a score below 8. It cleared both bars by a hair.

in plain words

If you let a model attach the severity label, you have let it grade its own homework in a subtler way than usual. It doesn't have to lie about what's wrong. It just has to call it minor. Any loop that gates on a model-assigned severity has a hole in it exactly the shape of that word.

What I'd actually do

My prior was half right, which is the least satisfying way to be right. The graph won — but not by producing better code, since the code was indistinguishable across 20,000 cases. It won by producing a test suite worth twice as much, and it charged 2.3× the tokens and 1.9× the wall clock for it.

More usefully, I don't think the win came from the graph shape. It came from one edge in it. Writing the tests was a separate node, with its own context, working from a decomposed contract — 122 criteria, 86 of them flagged as edge cases — rather than from the implementation sitting in the same conversation. The loop's tests inherited the implementation's blind spots because they were written by the same agent, in the same breath, holding the same interpretation of the spec.

So, concretely:

  • If the tests are the durable asset — backend logic somebody else will edit in six months — split test authoring into its own node with its own context. That single decision is what bought the 11/11. You don't need the rest of the graph to get it.
  • If it's a script, a prototype, something you'll review yourself before it matters — take the loop. Same correctness, half the cost, half the time.
  • Either way, never let a critic's own severity label be the last gate. Put something behind it the model cannot grade away. A mutation score is cheap: eleven mutations took me one script and about four minutes of compute, and it broke a tie that 23 hand-written tests and 20,000 random inputs couldn't.

Where this stops being true

This is n = 1. One feature, one model, one afternoon. Treat the direction as a finding and the magnitudes as anecdote.

The bigger caveat is my own spec. I wrote it to be gradeable — every formula, every threshold, every exception string nailed down — which is exactly the condition under which a strong model doesn't need help interpreting anything. That choice made the benchmark clean and, I suspect, made it as unfavourable to the graph as it could possibly be. The graph's first node exists to turn ambiguity into 122 explicit criteria, and I handed it a spec with almost no ambiguity left to convert. On a vague ticket, on a real one, I'd expect that gap to open rather than close — but I haven't measured it, so that's a hypothesis, not a result.

The thing I'd defend without qualification is smaller and more boring than either camp's position: write the exam before the agent starts, keep it where the agent can't reach it, and check that your own harness is standing in the right directory.
