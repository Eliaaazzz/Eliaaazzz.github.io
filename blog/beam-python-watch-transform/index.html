Watch: a polling transform for things that grow

"Process every file that lands in this bucket — including the ones that haven't landed yet" sounds like one line of code. It's actually a distributed-systems problem about memory, duplicates, and time. This is the story of porting Beam's Watch transform from Java to Python: how to use it, how a polling Splittable DoFn works inside, and how careful code review made it much better.

A deceptively simple ask

Every data team eventually writes this ticket: "Files arrive in a bucket throughout the day. Process each one exactly once, as soon as it appears. Don't stop."

Outside a distributed pipeline you'd reach for a loop: list the directory every thirty seconds, keep a set of filenames you've already handled, process the new ones. Twelve lines, done. Now put that inside a streaming pipeline running on a cluster, and each innocent phrase becomes a hard question:

  • "keep a set" — where? The worker that polled last time may be dead. The set must live in durable, checkpointed state, and it must not grow without bound over a watch that runs for months.
  • "exactly once" — the pipeline retries work when bundles fail. A retry that re-polls will see the same files again. Who filters the duplicates?
  • "as soon as it appears" — downstream, someone windows by event time. What watermark does a directory listing report, and when can a window covering 14:00–14:05 safely fire?
  • "don't stop" — but a test, a backfill, or a bounded job must stop. Where does the termination policy live?

The Java SDK answered all four questions years ago with a single elegant transform: Watch.growthOf(...) — the engine underneath its file-watching utilities. The Python SDK had no equivalent. In part one I described bringing unbounded sources to Python for GSoC 2026; once that machinery existed, Watch was the natural sequel. It merged as PR #39023, an experimental transform in apache_beam.io.watch.

The Watch idea: sets that only grow

Watch generalizes the ticket beautifully. Forget files for a second. The abstraction is:

For each input element, there is a set of outputs that only ever grows. You can't subscribe to changes — you can only poll the current set. Watch polls it for you, emits each output once the first time it's seen, tracks event time, and stops when a termination condition says so.

The input element is a thing to watch — a directory, a table name, a job id. The growing set is what's in it so far — files, partitions, completed shards. This one shape covers a surprising amount of ground: new files under a prefix, new partitions of a Kafka topic, new shards of a completed export, new rows of an append-only audit table.

Java spells it Watch.growthOf(pollFn); Python spells it Watch(poll_fn, ...). Same semantics, same building blocks — a poll function, a poll interval, termination conditions — with Python idioms where they earn their keep.

Meet the Python API

The whole public surface is small enough to hold in your head:

the API at a glance
from apache_beam.io.watch import (
    Watch,            # the PTransform
    PollResult,       # what your poll function returns
    PollFn,           # optional base class for poll functions
    never,            # termination: poll until PollResult.complete
    after_total_of,   # termination: stop N seconds after first seeing an input
)

watched = inputs | Watch(
    poll_fn,                       # input -> PollResult
    poll_interval=5,               # seconds (or a Duration) between polls
    termination=after_total_of(3600),
)
# watched: an unbounded PCollection of (input, output) pairs

Your poll function receives one input element and returns a PollResult — the current outputs, plus a claim about completeness:

  • PollResult.incomplete(outputs) — "here's what exists so far; more may come, keep polling me."
  • PollResult.complete(outputs) — "this is everything there will ever be; stop polling this input."

Each output can be a plain value or a TimestampedValue carrying its event time — when the thing actually happened (a file's modification time, a row's commit time). Watch preserves that timestamp on the emitted pair and uses it to advance the watermark, so downstream event-time windowing just works.

Tutorial: watch a directory, process new files forever

Let's write the ticket from the introduction, for real. Two files, zero magic. As in part one, the poll function lives in its own importable module so remote workers can reconstruct it.

watch_landing.py
import glob
import os

from apache_beam.io.watch import PollResult
from apache_beam.transforms.window import TimestampedValue
from apache_beam.utils.timestamp import Timestamp


def list_csv_files(directory) -> PollResult[str]:
  """One poll round: report every .csv currently in `directory`.

  The return annotation `PollResult[str]` is load-bearing: Watch reads
  it to infer the output coder (here, a UTF-8 string coder). No
  registration ceremony needed.
  """
  outputs = []
  for path in sorted(glob.glob(os.path.join(directory, '*.csv'))):
    mtime = Timestamp.of(os.path.getmtime(path))   # event time = mtime
    outputs.append(TimestampedValue(path, mtime))
  return PollResult.incomplete(outputs)            # more files may come
run_watch.py
import apache_beam as beam
from apache_beam.options.pipeline_options import PipelineOptions
from apache_beam.io.watch import Watch, after_total_of

from watch_landing import list_csv_files


def process(path):
  print(f'processing {path}')
  return path


with beam.Pipeline(options=PipelineOptions(streaming=True)) as p:
  (p
   | 'What to watch' >> beam.Create(['./landing'])
   | 'Watch it'      >> Watch(
         list_csv_files,
         poll_interval=5,                  # look every 5 seconds
         termination=after_total_of(600))  # give up after 10 minutes
   | 'Just the path' >> beam.MapTuple(lambda directory, path: path)
   | 'Process once'  >> beam.Map(process))

Run it, then drop files into ./landing from another terminal and watch them get picked up:

another terminal
$ echo "1,hello" > landing/a.csv
# within 5s:            processing ./landing/a.csv
$ echo "2,world" > landing/b.csv
$ echo "2,world" > landing/b.csv      # touch it again — no reprocess
# within 5s:            processing ./landing/b.csv

Three behaviors to notice, because they're the whole reason Watch exists:

  • Each file is processed once, even though every poll re-lists every file. The dedup is Watch's job, not your poll function's — list_csv_files is gloriously stateless.
  • Each emission carries the file's mtime as event time, so you could window downstream by when files actually landed.
  • It stops. After ten minutes of wall-clock time per watched input, after_total_of(600) ends the polling loop — which is what lets tests and backfills complete. Use never() for a true forever-watch that only PollResult.complete can end.
Scaling the same idea

Because the input is a PCollection, watching a thousand directories is beam.Create([dir1, dir2, …]) — each input gets its own independent polling loop, its own dedup state, and its own termination clock, spread across the cluster by the runner. That per-element independence is the SDF machinery from part one earning its keep.

The fine print that matters

What counts as "the same output"? By default, the output value itself is the dedup key. Sometimes that's wrong in interesting ways. Say your poll returns file metadata — path plus size — and a file gets appended to between polls. Same path, new size: by default that's a "new" output. If you want one emission per path, ever, give Watch a key function:

choosing identity
Watch(
    poll_file_metadata,
    poll_interval=5,
    output_key_fn=lambda meta: meta.path,   # dedup by path only
)

And if you want the opposite — re-emit when the same value reappears with a new event time (think: reprocess a file each time its mtime changes) — use_timestamp=True folds the timestamp into the dedup key.

Keys must encode deterministically. Watch dedups by hashing the encoded key, so two equal keys must encode to identical bytes on every worker, today and after a restart. Watch converts your key coder to its deterministic form and — this was a review point that made the API stricter and better — refuses coders that have none, at pipeline construction time rather than as silent wrong answers at 3 a.m. (Python's default fallback, pickling, can encode equal dicts differently. You want the loud error.)

Watermarks. Your poll function may attach an explicit watermark (PollResult(...).with_watermark(t), or via incomplete(..., timestamp=)); otherwise Watch infers one from the earliest new output in the round. Either way, event-time windows downstream see honest progress. PollResult.complete is sugar for watermark = end-of-time — which is exactly why it stops the polling: nothing can ever be newer.

Inside: what a polling SDF looks like

Under the hood, Watch is one Splittable DoFn — _WatchGrowthDoFn — and its restriction is not a byte range but a little state machine called the growth state. For a healthy polling loop it holds three things:

  • the completed set — a 128-bit BLAKE2 hash of every output key emitted so far, each mapped to the event time it was first seen (hashes, not values: state stays small even when outputs are fat);
  • the poll watermark — the event-time high ground reached so far;
  • the termination state — whatever the condition needs to decide "stop now?" (for after_total_of: when this input was first seen).

Each SDF invocation is exactly one poll round:

one poll round (annotated shape of process())
def process(element, tracker, watermark_estimator):
  result = poll_fn(element)                  # 1. poll — BEFORE claiming,
                                             #    so a slow poll never blocks
                                             #    the runner's checkpoints
  new = never_seen_before(result, completed) # 2. dedup vs hashed history
  if not tracker.try_claim((new, term_state)):
    return                                   # 3. runner checkpointed us —
                                             #    emit nothing this round
  for out in new.outputs:                    # 4. emit only the new outputs,
    yield (element, out.value)               #    at their event times
  advance_watermark(...)                     # 5. explicit or earliest-new
  if termination.can_stop_polling(...):      # 6. maybe stop…
    return
  tracker.defer_remainder(poll_interval)     # 7. …or nap and poll again

Step 7 is the loop. There is no while True anywhere — the SDF says "checkpoint me, wake me in five seconds," and the runner owns the schedule. That's what makes ten thousand concurrent watches cheap: sleeping watches are just rows of durable state, not parked threads.

Step 1 hides my favorite small design decision. An early version polled while holding the claim; review pointed out that a slow poll (a listing of a huge bucket, a slow HTTP call) would then block the tracker lock — the very lock the runner needs to take checkpoints. Polling first, claiming after, means the expensive part runs lock-free and the claim is a quick validation.

The replay trick: exactly-once emissions under retry

Here's the sneaky failure mode. A poll round emits files c and d… and then the bundle fails before the runner commits it. The runner will retry. If the retry polls again, the directory may have changed — e arrived — and now "what did the failed bundle actually promise downstream?" has no clean answer.

Watch's answer is to make the checkpoint itself deterministic. The growth state has a second variant — a replay state. When the runner checkpoints an in-flight round, the split produces:

  • primary → a replay state containing exactly the outputs claimed this round. If the bundle retries, it re-emits precisely those — no fresh poll, no drift.
  • residual → a polling state whose completed set already includes this round's keys, resuming the loop later.

This is the same primary/residual algebra from part one, bent to a new shape: the "position" being claimed isn't a byte offset, it's an entire poll round. Once you see restrictions as "any divisible description of work," SDF stops being exotic.

What code review fixed (a love letter to reviewers)

The version that merged is meaningfully better than the version I proposed, and the diff between them is a free education. A few of the seven review threads from my mentor:

  • "Why is planning tangled with emission?" → The round's bookkeeping got refactored into a pure planning function feeding a claim, so the DoFn body reads as the seven-step recipe above rather than interleaved state mutation.
  • "What happens with a non-deterministic key coder?" → It used to hash whatever bytes came out. Now it raises at construction with a message telling you exactly which coder to fix. Wrong-by-construction beats wrong-at-runtime.
  • "Your output types should fall out of expand()" → The transform now derives (input, output) type hints from the input's element type and the resolved output coder, so downstream coder inference never silently falls back to pickling.
  • "Docstrings accrete history" → After three rounds of review edits my docstrings read like changelogs. Rewrote them fresh, each fact stated once. (This one is now a personal rule.)

A follow-up PR from the same review energy, #39547 (merged), taught the coder inference to convert typing and native generic hints — so -> PollResult[str] and friends resolve to efficient coders across Python versions.

Keeping state bounded: the timestamp cursor

One honest cost of the design so far: the completed set grows by one 16-byte hash per output, forever. For a watch that emits millions of outputs over months, "forever" is a budget line. The fix in review (#39090) is my favorite kind of optimization — an observation, not a mechanism:

If every output your poller reports carries an event time, and you track the high-water mark of times whose outputs are all already emitted, then any future poll result older than that mark must be a duplicate — you can drop it without ever consulting the set. So hashes below the cursor can be evicted from state.

The completed set becomes a recent window plus an O(1) timestamp cursor, instead of an ever-growing archive. On a long-running benchmark the bounded state and cheaper rounds deliver about 4.1× the sustained throughput. The subtle part — caught in review, of course — is that the cursor must be pure progress metadata: encode items into it and you've just rebuilt the unbounded set with extra steps. It's three fields and an invariant, with tests asserting the state's size stays flat while the watch keeps emitting.

MatchContinuously, rebuilt on Watch

Remember the original ticket — files in a bucket? Beam's file connector has a transform for exactly that, fileio.MatchContinuously, historically built on a periodic impulse: a timer fires every interval, each firing lists the pattern, and a stateful ParDo drops paths it has seen. It works, but the dedup lives in a side structure with its own lifecycle quirks — and "process each file once across restarts" is precisely the promise Watch makes natively.

So the capstone of this arc (#39461, in review) rebuilds MatchContinuously on Watch: the file pattern becomes the watched input, one poll round is one fileio match, and the existing user options map onto Watch's knobs — dedup by path, or by path + modification time for "reprocess files when they change" mode. Users keep the API they know; the semantics underneath become the checkpointed, replay-safe ones you just read about.

the user-facing payoff
from apache_beam.io import fileio

files = (p
  | fileio.MatchContinuously(
        'gs://my-bucket/landing/*.csv',
        interval=30,                       # poll every 30s
        stop_timestamp=end_of_backfill)    # or run forever
  | fileio.ReadMatches()
  | beam.Map(process))
# same transform users already write — Watch semantics underneath
